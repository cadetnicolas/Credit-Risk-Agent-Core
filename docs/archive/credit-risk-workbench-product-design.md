# 信贷风险研究工作台：产品设计草案

状态：待评审。2026-11-06。本文从用户工作、商业价值和现有代码能力重新设计；不以仓库中的既有产品设计或需求文档为输入。文中的指标阈值、角色权限和数据字段是产品建议，实施前须用目标机构的数据与流程核定。

## 1. 产品判断

**一句话定位：**给信贷风险团队一个从存量资产异常发现，到可复核分析、建模实验和人工决策建议的统一工作台。

它降低的是完成一次**合格研究**所需的数据准备、口径确认、方法选择和报告整理成本，而不是取消专业判断。系统负责检查、计算、记录和解释计算路径；分析师负责判断业务含义；模型负责人和独立复核人员负责模型使用决定。所有结论都可以追到数据快照、指标定义、代码版本和运行记录。

两个相互连接的工作场景：

1. **资产监控与归因：**识别已放款组合的风险变化，判断变化来自客群结构、迁徙、成熟度还是特定分群，并形成待验证的处置建议。
2. **建模与回测：**把监控中发现的问题转成可复现实验，完成标签、样本、特征、训练、时序验证、业务回测和模型审阅。

两条工作流共享数据契约、指标口径和证据包，但各有独立入口。产品不直接审批贷款、不自动改线上策略、不把相关性描述为因果性，也不把离线回测收益当作已实现的坏账改善。

### 1.1 基础建设的现实边界

跨岗位减少重复工作是长期结果，不能把“完整报表系统、全域数据集市、全量数据治理、全面知识库”设为产品上线前提。它们涉及多个数据所有者和长期口径维护，若全部由本产品承建，首个用户价值会被基础项目推迟。首版采用**一个业务问题、一组授权数据、少量已签收口径、一条可复现工作流**的纵向切片；验证价值后才扩展产品和岗位。

产品与基础设施的分工：已有 BI 报表继续服务日常看数；已有数仓/集市是优先数据源；已有数据质量平台的检查结果可接入。工作台新增的是跨报表的调查过程、分析计算、实验复现和证据追溯。没有现成集市时，可在客户环境用只读视图或一次冻结的授权样本启动试点，但不把临时样本伪装为持续监控能力。

| 基础条件 | 可交付的产品能力 | 必须暂停的承诺 |
| --- | --- | --- |
| 有稳定历史数据、明确口径和定期刷新 | 周期监控、异常调查；若标签与时点特征可用，再做建模 | 无需暂停，但仍需验证每个新用例 |
| 有授权数据，但口径冲突或刷新不稳 | 一次性数据体检、手动触发的研究分析、口径签收 | 自动预警、跨期可靠比较和生产级模型评价 |
| 缺关键事件、观察时点或合法访问权限 | 数据缺口报告、字段清单和最小补数方案 | 风险归因、自动建模及效果承诺 |

最小监控切片需要稳定账户键、放款/观察日期、余额或笔数分母、还款/逾期事件、一个可解释的分群字段，以及至少可覆盖所选指标观察窗的历史。最小建模切片另需结果标签、成熟样本、特征在使用时点的可得性证明。具体历史长度由观察窗和业务周期确定，不预设统一月份数。缺少这些条件时，系统输出缺口与可做范围，不生成看似完整的结论。

### 1.2 相对通用 Agent 的产品理由

通用 Agent 已能读取文件、运行代码、调用工具、分析表格、生成报告，并逐步支持持久任务和团队协作。单次问答、自动绘图、生成 SQL 或模型训练脚本可以交给现有 Agent；把这些能力包装为“信贷专用聊天框”不足以支持独立采购。

专用产品的增量必须来自**长期运行的业务状态和可验证的工作结果**：接入已授权的生产数据切片，持续按同一口径发现异常；让不同岗位在同一异常、调查、决策和后续观察记录上协作；保存证据、口径版本和人工责任；积累误报、处置与后续结果，用于改进监控流程。建模能力服务这条闭环，例如为反复出现的风险变化建立候选预警模型，而非把训练模型本身作为主要卖点。

商业切入口优先选“**资产异常调查与处置复盘**”：它是周期性任务，有多个责任人、明确交接和可测的处理时间。首版不声称自动提高资产质量；先证明可信异常的调查速度、可复核性和处置闭环率。若客户已有通用 Agent 加少量脚本即可达到同等结果，且不需要跨期状态与责任流转，应交付可复用工具/Skill，而不单独建设业务应用。

实施前用同一客户数据和同一问题做对照：一组用现有通用 Agent 加授权工具，一组用专用工作流。比较端到端耗时、数字与口径错误、重复准备工时、跨岗位交接成本、复现率以及持续维护成本。专用产品只有在这些指标上形成明确净收益时进入下一阶段。

### 1.3 策略、特征与建模的产品形态

这三类研究共用一个实验契约：冻结数据快照、业务目标与时间点、候选生成方法、约束、训练/验证/样本外切分、人工审阅、运行产物和适用边界。实现上采用三层：通用 Agent 理解问题与提出假设；结构化工作流确认目标、数据和审阅节点；确定性计算引擎批量搜索、训练和验证。Agent 的文字结论引用计算产物，不用语言模型直接判断规则或特征的真实效果。

| 领域 | Agent 适合做 | 需要专用工作流/引擎做 | 商业价值与边界 |
| --- | --- | --- | --- |
| 策略挖掘 | 解释业务目标、提出分群和规则假设、总结权衡 | 在授权字段和约束下搜索候选；检查覆盖、坏账率、金额、稳定性、重叠和样本外表现；记录人工选择与后续验证 | 候选评估更快、更少无效试验。历史已放款样本可评估缩减客群的描述性结果；被拒人群没有还款结果时，不估计新增通过者的真实坏账率或上线收益 |
| 特征挖掘 | 从业务问题提出字段、聚合窗口和派生表达式；说明可解释性 | 检查评分时点可得性、字段血缘、泄漏、缺失、稳定性、冗余、增量效果及计算成本；人工确认入模 | 缩短可用特征筛选时间。单变量 IV、相关性或大规模枚举不能单独证明业务增益；若已有成熟特征平台，优先接入而非另建 |
| 分析建模 | 把目标转成实验计划、解释失败原因、比较候选 | 固定标签和样本、建立基线、时间外评估、校准与分群检查、实验版本、复核材料 | 缩短从研究问题到可审阅候选的周期。模型训练算法本身易被通用平台替代，价值取决于可复现性、验证质量和与决策流程的衔接 |

**策略挖掘的关键限制：**候选规则的命中率与历史坏账率可以从已观察样本计算，但“采用后会少坏多少账/多赚多少”是另一个问题。若要估计新策略相对历史策略的业务效果，需有足够的历史决策、可比人群和适当的试验或可信评估设计。缺少这些条件时，结果只作为候选排序和人工小范围验证依据。搜索大量候选还需控制过拟合：在独立时间段复核、报告尝试数量，并避免用同一份样本既筛选又宣称验证成功。

**投资顺序：**先将现有分析、规则挖掘和建模函数作为受权限约束的工具提供给通用 Agent；再为重复使用、风险高的步骤增加结构化工作流与不可变实验记录。若客户的策略团队愿意实际评审并试验候选，策略研究可以成为独立付费模块。特征挖掘通常作为建模模块中的能力；建模模块只有在样本时点、复核和交付周期上形成可测收益时才单独销售。

### 1.4 当前分析建模能力的最小实现决定

若目标仅是让 Agent 完成仓库里已有的一次性分析、特征筛选、训练和评估，**现有计算库封装为工具并接入通用 Agent 平台就是主路径**。此阶段不以新的业务前端、业务数据库或另一套 Agent 运行时为前提。自然语言交互、规划、权限、长任务、产物和人工控制优先复用通用平台；一次实验的规格与结果可以先作为不可变产物保存。

封装不等于把任意 Python 函数直接暴露给模型。建议少量按业务步骤组织的工具：`inspect_dataset`、`profile_sample`、`select_features`、`train_candidate`、`evaluate_candidate`、`mine_rule_candidates`、`simulate_cutoff`。输入使用数据集引用、已确认的标签/时间/字段绑定和参数；DataFrame 留在受控计算进程。输出分成供 Agent 理解的小摘要和供人复核的完整产物。训练、搜索等重任务通过平台持久作业执行；错误返回“缺标签定义、样本不足、字段越权、训练失败”等可操作状态。人工确认特征和解释结论留在工作流节点。

这一阶段与独立产品的差异在于**状态所有权**：工具接入解决一次请求的执行；专用产品才需要长期维护监控定义、异常队列、跨岗位责任、策略试验、审批和上线后结果。只有客户为这些持续状态和闭环付费，才增加业务服务与业务前端。现有计算函数本身不构成独立产品优势。

## 2. 目标用户与实际任务

| 角色 | 今天的难点 | 工作台要帮他完成的任务 | 保留的人为责任 |
| --- | --- | --- | --- |
| 风险负责人 | 报表很多，但异常的规模、可信度和处置优先级不清楚 | 每周看到需要行动的组合变化、影响敞口和证据 | 决定调查及处置优先级 |
| 风险分析师 | 多表取数、重复写 SQL、口径争议、异常归因慢 | 从预警钻取到分群、Vintage、迁徙及结构分解，输出可复核结论 | 审核口径、解释业务机制 |
| 建模分析师 | 标签与观察窗定义反复返工，特征泄漏难排查，实验难复现 | 用受引导的实验流程建立基线、对照和时序回测 | 决定特征、算法及适用边界 |
| 模型负责人/独立复核 | 只见单个 AUC 或 KS，难审查样本、稳定性和假设 | 查看实验差异、验证包、限制及审批记录 | 批准或否决模型使用 |
| 数据工程师 | 反复应付临时口径和数据质量问题 | 维护源表映射、快照、质量检查和血缘 | 修复上游数据及授予访问权 |

首批采购方是有存量信贷资产、分析团队和可查询历史数据的机构。首批高频使用者是风险分析师与建模分析师。先选择一个岗位的一个高频问题作为试点；另一岗位通过复用同一证据包受益，再逐步扩展。对数据条件不足的机构，先交付有边界的数据可用性评估，而不是把完整数据集市建设隐含进产品实施。

## 3. 用户体验：从问题到证据

### 3.1 入口与信息架构

本节描述独立产品成立后的体验。当前分析建模阶段先使用通用 Agent 的交互与任务能力，通过工具和结构化输入完成一次性研究；不把通用框架演示 `/app` 直接改成业务产品。若持续工作流价值在试点中成立，再新建业务前端：首页设置**看风险变化**、**解释一个异常**、**发起建模实验**三个任务入口；全局进入数据集、口径、实验、证据包和管理设置。自然语言是任务入口之一，关键选择必须可见、可改。

共同的分析页由四栏组成：顶部是本次问题与时间范围；左侧是样本和口径；中间是图表与表格；右侧是系统建议、检查结果和证据。用户可以从任何图上的点进入同口径的明细分群，并看到分母、样本量、覆盖率、区间和数据更新时间。系统生成的文字逐条绑定图表或计算结果，未经验证的解释显示为“待验证假设”。

### 3.2 资产监控流程

1. **建立监控对象。**选择产品、放款批次、在贷状态、机构、渠道等范围；设定观察频率和关注指标。系统预览历史覆盖、样本量、口径变化和可用分群。
2. **读异常。**首页按影响金额、恶化幅度、持续时间和数据质量排序。一个异常卡片展示基线与当前值、敞口、样本量、成熟度和数据延迟；数据质量不足时标为“暂不可判断”。
3. **查原因。**先做同口径时间比较，再看 Vintage、逾期迁徙、客群结构变化和分群内部变化。结果区分“结构贡献”“组内变化”“共同变化”及无法解释部分。小样本、Simpson 反转、口径变更、观察窗未成熟均显式提示。
4. **形成调查结论。**分析师选择“数据问题、组合变化、疑似风险变化、尚不能判断”，记录证据、反证、下一步核查人和截止时间。系统可起草报告，但不能自动宣称因果或处置有效。
5. **跟踪结果。**调查状态、人工处置、后续指标和关闭理由关联原异常。产品统计发现到验证的耗时，不把发现一条异常本身当作业务收益。

例：某渠道近两期 30+ DPD 上升。系统先核对账龄与数据延迟，再展示同账龄 Vintage、余额加权与笔数口径、渠道内部客群变化。若渠道内每个客群风险稳定而高风险客群占比提高，提示“结构变化解释了主要增幅”，并给出分解表；不直接建议停掉渠道。

### 3.3 建模与回测流程

1. **实验意图。**用户选择预测目标、使用时点、业务对象和使用方式。系统将自然语言请求转换成可编辑实验规格，并解释所需字段。
2. **标签和样本。**固定观察时点、表现窗、坏样本定义、排除规则、去重粒度和成熟样本截止日；展示事件率、覆盖、删样原因、月度分布及可能的选择偏差。定义不完整时禁止训练。
3. **特征检查。**只允许使用评分时点已知的数据；按可用时间检查泄漏，显示缺失、稳定性、异常值、单值、群体差异及业务含义。系统给出建议，用户确认特征清单与排除理由。
4. **建立基线与候选。**先运行简单、可解释的基线，再允许配置候选模型和有限的参数搜索；所有实验共用冻结的数据快照、时间划分和标签。自动化为建议值，不替用户决定建模目标。
5. **验证与回测。**以时间划分做开发集、验证集和样本外测试；展示区分度、校准、分箱坏账率、跨月表现、稳定性、关键分群表现、置信区间及样本量。业务阈值模拟显示覆盖、风险、收益假设和不确定性；历史选择机制不明时标注“不能估计真实上线效果”。
6. **审阅与交付。**生成可复现的模型卡：数据和标签、特征清单、代码与环境版本、所有对照实验、失败尝试、局限、验证结论和人工审批。模型可以进入“候选、复核中、已批准供特定用途、停用”状态；部署由外部受控流程执行。

对低经验用户提供“为什么需要此设置”的短说明和安全默认值；高级用户可展开完整参数、SQL 和中间表。任何自动选择都有理由、可修改入口和更改记录。不能只输出一个综合评分或“推荐上线”。

## 4. 功能需求与验收口径

| 模块 | 首版必须做到 | 不合格输出的处理 |
| --- | --- | --- |
| 数据接入 | 首个用例只接一个授权数据切片；优先复用现有集市或只读视图，登记数据所有者、刷新频率、主键、时间字段和敏感级别 | 缺主键/观察时点/权限时停止相关任务 |
| 语义口径 | 只维护试点实际使用的少量指标；每项包含分子、分母、权重、账龄、观察时间、过滤条件、签收人和版本 | 指标版本不同不直接拼接趋势 |
| 数据质量 | 在每次任务运行时检查该任务依赖字段的完整性、唯一性、及时性、值域和跨期变化；复用已有平台结果 | 未达门槛则降级展示或阻断模型实验 |
| 监控 | 趋势、Vintage、迁徙、分群、结构分解、敞口与调查闭环 | 告警注明样本量、基线和迟到数据 |
| 建模 | 标签检查、特征时点检查、基线、候选训练、样本外评估、实验对照、模型卡 | 标签不成熟或泄漏时不出“可用模型” |
| 助手 | 把问题转为可编辑计划，调用受权限约束的确定性工具，引用结果并解释限制 | 工具失败或证据不足时说明原因并请求人工判断 |
| 治理 | 租户隔离、字段级遮蔽、角色授权、审批、审计、数据与模型留存策略 | 越权请求拒绝并留下审计事件 |

**发布验收示例：**同一份快照和规格重复运行得到相同指标；任一报告数字能回到查询、口径和快照；错误时间特征会阻断训练；未成熟标签不能产生样本外性能结论；不同租户无法看到对方数据；一次异常可从发现走到人工关闭。验收数据使用脱敏或合成数据，真实数据由客户在授权环境验证。

## 5. 商业设计

### 5.1 价值假设与购买理由

第一价值是**缩短从异常出现到可信解释及责任人接手的时间**，第二价值是**让调查、处置与结果复盘形成可追溯记录**，第三价值是**减少由监控问题引出的建模试验重复准备和无法复现的结果**。这些是可通过试点测量的过程与质量收益；坏账降低、利润增加属于后续业务假设，不能由离线回测直接证明。

试点选择一个有明确负责人、历史数据和固定分析节奏的组合，先用短期数据可行性检查确定可做范围，再记录实施前的人工耗时基线，运行一个完整的监控或建模场景。观察：异常到首次可信结论的中位耗时、每次模型实验人工准备时长、报告可复现率、被质量检查阻断的错误、活跃分析师占比、误报/漏报复盘。业务结果单独按可比组合和足够长的表现窗评估，不承诺短期坏账改善。

试点必须增加一项购买检验：同样的数据和授权工具交给客户已有的通用 Agent，比较其交付质量和总成本。若专用工作台的优势仅体现在首份报告排版或提示词便利，就把计算函数提供为可连接的工具；只有跨期监控、多人协作、责任闭环和结果反馈产生明显增益，才推进独立产品销售。

### 5.2 商业化与落地方式

面向机构提供企业私有部署或客户控制的云环境。合同先设一个有边界的数据可行性阶段：约定数据切片、字段清单、口径签收人与验收结果；通过后再进入单场景试点，最后按扩展的组合与计算量采购。正式合同可包含平台基础费、数据接入实施费和计算/存储资源项；不按“发现多少风险”或“模型提高多少 KS”收费，避免推动虚假告警或指标优化。试点只承诺一条完整工作流、用户培训、审计与安全验收，以及可导出的证据包，不预售跨岗位的全面覆盖。

采购中的核心异议是数据不能外流、模型不可解释、口径无法信任、接入成本高。对应交付是租户隔离与私有部署、模型卡与人工复核、口径版本与追溯、先接一个组合和最少字段。可行性阶段必须统计客户数据准备的人天和长期维护责任；若接入成本长期高于可测的节省，停止扩展或转为客户自己的数据工程项目。

## 6. 数据与方法契约

数据按事件时间与可用时间分开保存。最小实体：借款人/账户的稳定匿名键、申请或放款事件、合同与余额快照、还款/逾期事件、渠道与产品维度、评分时点可用特征、模型分数、人工或系统决策记录。建模还需要可定义的观察窗和结果事件。敏感身份信息在分析层只保留所需的匿名键，数据访问受客户授权控制。

上述是逐步扩展的数据目录，首个场景只要求其实际使用的字段。接入层保存源字段到业务字段的映射、来源、负责人、刷新时间与已知缺陷；口径仅由有权负责人签收。知识库先包含这批**已签收口径、字段解释、分析方法说明和经审核的历史案例**。Agent 可检索它们解释流程，但数字事实只能来自当前数据产物；知识缺失时要求用户确认，不能自动编造口径。每新增一个用例才增加相应知识条目和维护责任，不建立覆盖全机构的百科式知识库。

所有运行保存 `dataset_snapshot_id`、`metric_version`、`label_version`、`feature_cutoff`、`analysis_spec`、`code_version`、`actor`、`run_id`、`created_at` 和结果校验值。图表和报告只能引用这些已落盘的结果对象。抽样、缺失值、权重、排除规则和统计区间属于结果的一部分。对于真实处置效果，必须另设计有对照的评估；普通分群比较只支持描述与假设生成。

预警阈值按客户的基线、样本量和业务成本配置；首版不内置“普适安全阈值”。模型选择不能只按 AUC/KS 排序，必须同时审视校准、稳定性、分群、可解释性、可操作性和数据可获得性。

## 7. 工程设计

### 7.1 边界与组件

1. **当前接入层：**在信贷业务包定义 Profile、严格输入 schema 和少量高层工具；通过通用 Agent 平台执行，不新建业务前端。DataFrame 与原始记录只在授权计算端读取。
2. **当前计算层：**把 `credit_risk_agent/src/credit_agent` 中现有的趋势、钻取、结构分解、Vintage、迁徙、阈值优化、样本检查、建模与评估函数包装为有类型输入输出的业务计算；缺失的时点检查、成熟度判断和证据包按实际用例补齐。
3. **当前运行层：**复用 `agent_platform` 的身份、租户 ACL、持久运行、异步作业、审批、产物和观测能力。Agent 负责理解问题、规划和解释；长时间计算由确定性工具完成。
4. **后续业务服务与前端：**仅在跨期监控、异常队列、多人责任和结果复盘经过客户试点验证后，新建业务状态服务与前端。业务表和界面留在信贷应用内，不把业务概念加入通用框架。

### 7.2 关键接口与执行规则

建议服务接口围绕资源而非聊天记录：`datasets`、`metric-definitions`、`monitor-definitions`、`alerts`、`investigations`、`experiments`、`model-cards`、`artifacts`。每个计算请求先校验数据权限和规格，返回 `run_id`；长任务返回状态和产物地址。报告引用不可变产物版本。任务失败保留可理解的错误类型和已完成步骤，重试使用幂等键。

Agent 工具只接收白名单数据集 ID、时间范围、维度和已验证的规格；SQL 访问只读、限定数据范围与扫描预算。模型输入只包含最小化摘要和抽样说明，不发送原始身份信息。输出生成前做数字引用检查：文字中的数值要能映射到产物字段；无法映射则删除或标为人工陈述。

### 7.3 质量与安全门

工程验收分四类：计算正确性与可复现、时间穿越和标签成熟度、权限与敏感信息、人工工作流。采用合成数据构造结构变化、真实组内恶化、口径变化、迟到数据、泄漏特征和不成熟标签等场景。真实业务口径由客户的数据所有者签收。上线前必须完成容量评估、成本上限、恢复演练和审计记录检查。

## 8. 分期交付

| 阶段 | 交付 | 退出条件 |
| --- | --- | --- |
| A：数据可行性 | 选一个问题和一个授权数据切片；完成字段映射、口径签收、质量体检与工作量估算 | 明确能做、不能做、补数责任和接入成本；不达标时暂停自动化承诺 |
| B：单工作流闭环 | 监控调查或建模实验二选一；完成输入、计算、证据、人工反馈 | 与现有人工流程相比，耗时或质量有可测改进，结果可复现 |
| C：相邻工作流扩展 | 先与通用 Agent 的同场景交付做对照；达到净收益后复用已验证的数据与口径，增加另一岗位的完整工作流 | 跨岗位交接减少重复取数和解释，新增口径有负责人 |
| D：持续运行 | 按数据稳定性增加自动预警、协作、更多组合和成本优化 | 定期刷新、误报复盘、权限和维护责任均运行稳定 |

首版刻意不做自动放款决策、线上策略发布、通用特征平台、任意 SQL 自助平台、无限制 AutoML、因果效果自动推断。这些需求需要独立的权限、数据和效果验证设计。

## 9. 需要业务方定稿的事项

1. 首个试点的资产类型、目标机构与部署边界是什么？这决定最小数据契约和敏感字段处理。
2. 监控的主口径是笔数、余额还是两者并列？风险事件的 DPD 与核销定义由谁签收？
3. 建模首个使用场景是贷前评分、贷中预警还是催收排序？每种场景的评分时点、标签和回测方式不同。
4. 现有数据是否保存评分时点可用特征及历史决策记录？缺少时，部分回测只能做研究模拟。
5. 谁拥有实验审批和模型使用批准权？产品必须映射机构现有的职责分离和留存要求。
6. 客户已有的 BI、集市、质量平台和知识管理分别由谁维护？试点能直接复用哪些授权视图与签收口径？
7. 首个用例的手工流程耗时和数据准备成本是多少？这是判断产品是否值得扩展的基线。
8. 客户当前使用哪些通用 Agent？同一场景下它们的实际成本和错误率是多少？这是独立产品购买理由的对照基线。

## 10. 参考原则与适用边界

设计参考了 [巴塞尔委员会 2025 年信贷风险管理原则](https://www.bis.org/publications/202504-guidelines-principles-management-credit-risk)中关于风险计量、监控及控制的结构，以及[美国联储 2026 年模型风险管理修订指导](https://www.federalreserve.gov/supervisionreg/srletters/sr2602.htm)中按模型风险和机构复杂度实施治理的原则。这些材料用于产品质量设计，不直接构成目标客户所在司法辖区的合规判断；部署时由客户法务、合规和模型风险团队确认适用要求。

通用 Agent 能力对照采用 [OpenAI Codex 官方文档](https://developers.openai.com/blog/codex-as-a-platform)和[腾讯云 WorkBuddy 官方产品说明](https://cloud.tencent.com/product/workbuddy)截至 2026-11-06 的公开描述。具体客户环境的连接器、权限和采购成本仍需试点核实。

实验边界参考 [scikit-learn 关于数据泄漏与交叉验证的官方说明](https://scikit-learn.org/stable/common_pitfalls)、[已批准贷款样本的选择偏差研究](https://arxiv.org/abs/2407.13009)和[离线策略评估的混杂问题研究](https://proceedings.mlr.press/v238/kausik24a.html)。这些来源支持设计中的时点检查与结论降级原则，不替代客户数据上的具体识别与验证。
