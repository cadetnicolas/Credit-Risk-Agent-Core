# 分析纪律（四规程共用）

> 本文件被 `credit-data-admission` / `portfolio-anomaly-attribution` /
> `policy-cutoff-simulation` / `scorecard-modeling-pipeline` 共同引用。
> 四条红线不分规程，任何时候都适用。修改时四个副本需同步。

以下每一条都来自实际发生过的事故，不是假想。

---

## 一、取数纪律

### 1. 需求方给了 SQL，就原样执行；要改，先问，不许先取

不改列、不加 `WHERE`、不换表、不改时间窗、不改排序。**多一列、加一个过滤，分母就变了**，而下游没有任何东西能看出来——数字还是那个形状，含义已经不同。

**这条是硬门槛，不是事后留痕。** 工具层已经这么做了：`download_sample` 必须收到需求方的 `user_sql`（原句），实际执行的 `sql` 与它不一致时**直接抛错拒绝执行**，不读数据、不落盘、不产生任何快照。预览同样受此约束——预览也会读到行。

因此**不存在"先按自己的口径取一份、再在结果里标注说明"这条路径**。数一旦出来，下游所有占比、分群、结论都建立在被改写过的口径上；标注撤不回这件事，只会在正确结论旁边多留一个错误结论。

- 需要更多字段时，先说清三件事：**现有字段为什么不够 / 要加哪几列 / 会改变什么口径**，等需求方回话。
- 需求方同意后，把**他的原话**填进 `authorization`（如 `同意加上产品维度和地区维度`），工具才放行，并把该原话写进 manifest 的 `deviation_authorized_by`。不得自行编造这句话。
- 二次取数**不得覆盖或替换**第一次的结果。扩列取数用新名字单独落一份，两份结论分开汇报。
- 怀疑原 SQL 有缺陷（例如 `appl_` 表其实是申请粒度而非放款粒度），**先说明判断依据并请求确认**，不要直接"修正"后执行。

**唯一不需授权的读取是元数据**（列名、类型、表名）：`desc <table>` 走 `schema()` 接口，不读数据行。

### 2. 每次取数写 `purpose`

`purpose` 必须包含**用途 + 授权来源**，例如：

- `需求方给定 SQL，原样执行`
- `经需求方同意扩列（加 loan_product/area_name）后取数`

写不出授权来源，说明还没拿到授权，此时也不该取。`download_sample` 对正式取数（非 preview）强制要求该字段；`user_sql` 缺失同样直接拒绝。

### 3. 数据边界先报，再分析

开跑之前先确认并写出来：**时间覆盖范围、标签缺失率、有效样本量、粒度**。

需求方说"样本都已满足表现期"不构成证据——必须自己查 `reloan_y` / 表现字段的按时间分布。若某月之后标签 100% 为空，那就是没有表现期，样本量再大也不能用于坏账结论。

### 4. 数据库凭证走配置链路，不读散落文件

凭证只从 `setup.html` → `config.json` → `.env` 这条链路来。不要为了"跑通"去读别的项目里硬编码 AK 的连接文件。配置改动后 `get_env_config()` 会自动检测文件指纹变化并热重载，不需要重启进程。

## 二、结论证据门槛

每条结论先归入三档之一，档位决定能写什么话。

| 档位 | 条件 | 允许的表述 |
| --- | --- | --- |
| **A 可下结论** | 关键口径已确认 + 样本量达标 + 做过统计检验 | "显著/不显著""恶化/未恶化" |
| **B 仅描述** | 方向可见但未检验，或样本不足 | "本期为 X%，上期为 Y%"，不给因果与定性 |
| **C 不得下结论** | 缺关键字段 / 标签未成熟 / 口径不明 | 只能输出"无法判定 + 缺什么" |

### 硬规则

1. **占比类结论必须同时给分子绝对数。**
   `27.25% → 33.85%` 单看像恶化；分子 `130 → 131`、分母 `477 → 387` 一看就知道是分母收缩。
   分子没涨而分母降了，只能写"占比被动抬升"，**不得写"客群恶化"**。

2. **阈值型指标必须做切点敏感性。**
   多头 ≥N、评分 ≥X 这类规则，至少换 3 个切点看方向是否一致。只有一个切点显著、相邻切点都不显著，是阈值选择产物，不是分布位移。同理，多个切点里挑一个显著的要说明多重比较。

3. **整体分布先检验，再看局部。**
   报告"某档占比升高"之前，先做整体分布检验（KS / 分位数 / 均值置信区间）。整体分布不显著、只有某个切点显著，说明变化是切点造成的，不能推及"客群变差"。

4. **单指标必须评估区分度。**
   任何被称作"风险指标"的变量，都要给 AUC / KS / IV / lift，并对照门槛：KS ≥ 0.30 才算可用，IV < 0.02 基本无区分力。达不到就写"弱变量，不宜单独作为规则"。

5. **规则与风险的相关性不能用同源标签自证。**
   用 `suspected_*`（疑似规则标签）去验证另一个规则变量，是循环论证。必须用**贷后表现**（逾期 / 坏账 / `reloan_y`）作为标签。没有表现数据时，明确写"该规则的有效性无法验证"。

6. **区分"统计显著"与"业务恶化"。**
   `z=+2.10` 只说明差异不像随机波动，不等于风险实质恶化，更不等于策略失效。样本量小的时候，置信区间比点估计更重要。

7. **无法判定时用固定三段式输出**：
   - 已确认什么（有数据支撑的部分）
   - 不能确认什么（缺什么证据）
   - 需要什么才能确认（具体到表名 / 字段 / 口径）

   **不要为了"给个交代"而把 B 档写成 A 档。** 宁可输出"当前数据无法回答"，也不要给一个会被推翻的结论。

## 三、报告表格

列多的表最容易出问题：每列被压到 1 个汉字宽，中文逐字换行，看上去像竖排。

- **不要用 `overflow-wrap:anywhere`**。它在计算最小宽度时就允许任意断行，导致列被压到极窄。用 `overflow-wrap:break-word` + `word-break:normal`。
- 给 `.tbl th` 设 `min-width:4.5em`、`.tbl td` 设 `min-width:3.2em` 保底。
- 容器 `.tbl{overflow-x:auto}`，宽表横向滚动，不要压列。
- 超过 6 列时：表头用短名，单位写进表头（如 `坏账率%`），数字列右对齐并 `nowrap`。
- 长 ID / 哈希列单独用 `font-family:monospace; word-break:break-all`，不要影响其他列。

## 四、两类典型事故（引用时请保留）

**事故一：擅自扩列改变口径。**
需求方给的 SQL 是 4 列，执行时加了 12 列和一个月份 `WHERE`。分母从"全部放款"变成"指定月份"，后续所有占比都失去可比性。事后靠对照原始 SQL 才发现。
**教训的形式很重要**：第一次修补只是"取完在 manifest 里标注偏离"，这等于承认"可以先扩大范围，只要补一句说明"。这是错的——标注不能撤回已经用错误口径算出来的结论。最终做法是**执行前拒绝**：`sql` 与 `user_sql` 不一致就抛错，除非带上需求方的授权原话。

**事故二：把分母收缩当成客群恶化。**
10 月多头 ≥10 占比从 27.25% 升到 33.85%，被直接解读为"客群恶化"。核查后发现分子从 130 变成 131（+1 人）、分母从 477 降到 387（−18.9%）。同时整体分布 KS 检验 p=0.233，完全没有变化。按相同分母折算，占比是 27.46%，与上期持平。

**共同点**：两个事故里，数字本身都没错，错在**没有先问"这个数的分母是什么、它真的变了吗"**。
